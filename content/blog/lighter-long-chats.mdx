A chat in Mains can run for hours. A single session might contain hundreds of tool calls, long command outputs, generated images, and several browser tabs. Each of those has a different memory cost: text in JavaScript, mounted React components, decoded image pixels, or a separate Chromium renderer.

Before [Mains 0.16](/blog/mains-0-16-release), opening a long conversation could keep almost 12,000 DOM nodes mounted, including messages far outside the viewport. We changed how history is loaded, how its rows are mounted, and how their contents are retained. The image pipeline now shares those limits across chat and Atlas, with native image processing on desktop and Sharp in the standalone server.

## Start with a window of history

Rendering fewer messages helps, but loading the entire conversation into JavaScript would still leave its text and tool payloads in memory. We moved the first limit into the history query.

Opening a conversation reads its latest **20 prompt blocks**. Older and newer requests move by 20 blocks and retain a window of at most **60**. A block includes a user prompt and the work that follows it, so paging preserves the structure of a turn. Outside the selected range, the backend examines chronological keys rather than loading message bodies.

The renderer replaces that window as you navigate. It retains event and turn data for only four recently viewed runs; reopening an evicted run fetches its latest page again. The complete history remains in the database, and the agent’s context is unchanged.

Paging also has to behave while an agent is working. When you scroll away from the latest message, the upper edge of the reading window freezes. Paging and refresh requests run in sequence, so a late refresh cannot overwrite the older page you just requested. A visible row’s identity and position anchor the scroll after replacement; **Jump to latest** explicitly returns to the live tail.

## Keep React close to the viewport

Within the loaded page, `TranscriptWindow` mounts only nearby row bodies. Its buffer is the larger of 800 pixels or one viewport height, giving messages time to appear before you reach them.

Rows outside that region keep a thin placeholder with a measured or estimated height. Their Markdown, tool details, and media components unmount. `ResizeObserver` updates the measurements as content changes; if a row above the viewport changes height, the scroll offset is adjusted to keep the reading position steady.

Unmounting must not make an accordion forget that you opened it. A separate cache remembers scroll offsets, row heights, and small interaction values for four views, with limits of 128 heights and 512 interaction values per view. It holds no message bodies, DOM nodes, images, or React trees. Inactive transcript tabs unmount their bodies too.

## Fetch tool output when it is opened

A collapsed command can still contain megabytes of output. Hiding its component would do little if the complete result had already crossed IPC and entered renderer state.

Desktop history requests defer completed Read, Bash, and Shell outputs longer than **16,384 characters**, excluding MCP app results. SQLite returns a **2,000-character prefix** and the original length. The full output stays out of backend JavaScript and the history response.

Expanding the row requests the original output for that tool call and its owning run. Closing it or moving it outside the rendered region releases the detail component and its fetched payload. Formatting happens inside mounted detail bodies, and event mapping no longer keeps another formatted copy of the same input and output strings. Pending tools and provider context retain their complete payloads.

## Give images a preview budget

An image’s file size is only part of its cost. A 4,000 × 3,000 image needs roughly **46 MiB** for one decoded, four-byte-per-pixel bitmap, before additional rendering allocations. Showing it at 200 pixels wide does not make that original bitmap smaller.

Chat attachments therefore load a derivative with a maximum edge of **256 pixels**. An intersection observer starts the request within 300 pixels of the viewport. Away from it, the attachment component keeps a layout placeholder and releases its image lease.

Opening an attachment loads a larger preview, capped at **1,600 pixels**. That preview belongs to the open modal and is released when it closes. Downloading requests the original file separately. Preview generation never rewrites the original.

Atlas uses the same backend pipeline: 256-pixel derivatives for list images, 768 for grids and page-card images, and 2,048 for page covers. Atlas’s full image viewer and editor embeds can still use the original. The appropriate size depends on the surface displaying it.

## Resize with Sharp on the server

Both hosts implement the same image-preview adapter. The Electron host uses `nativeImage`; the standalone Node server uses **Sharp**. Their shared backend handles authorization, request deduplication, the decode queue, and the disk cache.

The core of the Sharp adapter looks like this:

```ts
sharp.cache({ memory: 8, files: 0, items: 16 });
sharp.concurrency(1);

const source = sharp(bytes, { animated: false });
const hasAlpha = preserveAlpha && (await source.metadata()).hasAlpha;
const resized = source.rotate().resize({
  width: maxSide,
  height: maxSide,
  fit: "inside",
  withoutEnlargement: true,
});
const encoded = hasAlpha
  ? resized.png()
  : resized.flatten({ background: "#ffffff" }).jpeg({ quality: 82 });
const { data, info } = await encoded.toBuffer({ resolveWithObject: true });
```

The resize preserves aspect ratio, avoids cropping, and leaves smaller images at their existing size. Sharp applies the source orientation before resizing. When transparency preservation is requested and the source has alpha, the output is PNG; otherwise this adapter produces a JPEG at quality 82, flattening transparency onto white. Animated sources are read as a still preview.

The backend serializes preview work, preventing a gallery from decoding many large originals simultaneously. Matching requests share an in-flight job. Sharp’s native cache is configured for 8 MB of memory, zero cached files, and 16 items, with concurrency set to one. These settings bound specific caches and processing work; they are not a total process-memory limit.

## Bound the caches as well

Derivatives live in `cache/image-previews`, with a **128 MiB disk-cache target**. Their keys include the source file’s identity, size, modification times, requested dimensions, and alpha policy. Changing the source invalidates the cached derivative. Reads touch the entry’s recency, and batched pruning removes the least recently used previews.

The renderer separately caches only the small attachment thumbnails, targeting **16 MiB and 64 entries**. Images currently in use stay valid; unused entries are evicted and their Blob URLs revoked. Larger attachment previews bypass this retained cache. Switching backends clears image entries so another host’s pixels cannot remain attached to the current conversation.

SVGs do not need raster resizing. Local formats that the host codec cannot preview can fall back to original-file serving within the existing file-size limit. The original stays the durable source; the derivative is disposable.

## Let browser tabs rest

The in-app browser has its own cost: each live page can hold a DOM, scripts, media, and application state in another Chromium renderer.

Mains targets **three live browser views**, hibernating the least recently used inactive tabs. This is a soft limit. The visible active tab, pages playing audio or loading, and pages that veto `beforeunload` stay alive. The existing two-minute timer for a hidden browser panel uses the same guarded hibernation path.

Before closing a view, Mains captures Chromium’s current-page state plus a bounded snapshot of ordinary form values, editable text, and scroll position. That state stays in an **8 MiB session cache**; disk persistence contains URLs and titles. Waking a tab restores its navigation history and attempts to restore its page state. Custom controls and arbitrary application JavaScript still depend on the page’s own persistence.

## What we measured

For the 0.16 transcript work, we rendered the production transcript components in an isolated Electron host using fixed snapshots of two real developer conversations. Offline IPC fixtures reproduced the production history ranges and deferred-output projection. Each comparison used fresh processes, a 1,100 × 800 window, a warm thumbnail cache, and three repetitions with alternating variant order.

The long conversation’s initial DOM dropped from **11,941 nodes to 280**. The accompanying checks verified row-height changes, accordion state, scroll restoration, inactive-row unmounting, and deferred output loading. All five attachment thumbnails in the image fixture had a maximum edge of 256 pixels.

We measured the actual browser service separately with six controlled pages, each containing 1,000 DOM cards and a touched 16 MiB buffer. Combined host and browser-tab renderer RSS fell from **749.1 MiB to 418.3 MiB**, a **44.2% reduction**, with three views live instead of six. This browser test used no forced garbage collection, and its savings depend on those page contents.

These measurements cover the desktop transcript and browser tests. They do not measure total Mains memory, agent processes, real MCP app frames, or the standalone Sharp adapter independently.

Paging trades lower retained memory for additional reads when you revisit history. Its turn limit is also not a byte limit: one turn can still contain a large message or many tool calls. Chromium may retain allocated memory after components unmount. We therefore look at memory after browsing and reopening content as well as at the first frame, while keeping the renderer’s loaded history, mounted rows, decoded previews, and caches bounded at their own seams.
